## 概述

M4 是一个**不打开 Godot 就能跑完一局**的命令行工具：喂它初始状态和种子，它用几种"脚本玩家"策略把整局跑完，输出一张指标表。

它是这个项目**最重要的工具**，原因有二：

1. §5.4 要求"不启动渲染也能跑完一整季"——**M4 就是那条验收方式本身**。没有它，架构约束只是一句口号。
2. 它让"平衡是否成立"变成**可测的数字**，而不是靠人试玩的感觉。一个人做游戏，最缺的就是测平衡的人手。

---

## 玩家幻想

玩家永远不会见到它。它保护的是玩家的体验：**你玩的这一版，是几千局跑出来的，不是拍脑袋定的。**

## 详细设计

### 核心规则

**R1 · 形态：独立控制台项目**

```
/Balance/
  Balance.csproj            → 引用 TianziGe.Sim（纯 C#，无 Godot）
  Program.cs                → CLI 入口
  Strategies/               → 脚本玩家策略
  Reports/                  → 输出 CSV + Markdown
```

- **不得引用 Godot 程序集**。这本身就是架构约束的持续验证：一旦有人把引擎依赖漏进 Sim 层，这个项目立刻编译失败。

**R2 · 三种脚本玩家策略（核心）**

| 策略 | 行为 | 期望 |
| --- | --- | --- |
| **勤奋** | 优先写满田；优先防御字；祟字立即清；地力 < 30 休耕 | 高守住率 |
| **偷懒** | 只写产出字；留 2–3 块空田；不防守 | 中低守住率 |
| **莽夫** | 全部写产出；开垦到底；清祟字只在不影响产出时 | 低守住率、高产出、早期崩 |

> **三种策略的差距就是游戏的深度指标。** 如果"勤奋"和"偷懒"的守住率差不到 15 个百分点，说明经营决策不重要，玩法没有深度。

**R3 · 输入**

```
seed            : 种子
seasonCount     : 季数（默认 4）
strategy        : 策略名
charTablePath   : 字表 JSON 路径
outputPath      : 报告输出路径
```

**R4 · 输出指标**

| 指标 | 说明 |
| --- | --- |
| `nights_per_season` | 每季祟夜次数（目标 1–2） |
| `hold_rate` | 祟夜三波全守比例 |
| `plots_destroyed` | 累计毁田数 |
| `coin_curve` | 每回合铜钱曲线 |
| `soil_curve` | 全田平均地力曲线 |
| `codex_coverage` | 字谱覆盖比例（收尾指标） |
| `finished` | 是否走到冬末 |
| `final_hash` | 终局状态 hash（复现校验） |

**R5 · 批量与可复现**

- `--runs 100 --seed-base 0` → 跑 100 局（种子 0..99）。
- 同一 `(seed, strategy, charTable)` 的 `final_hash` **必须完全一致**——这是 F2 确定性的回归测试。
- CI 里跑 `--runs 20` 作为构建门禁（超过 60 秒则降级为夜间任务）。

**R6 · 平衡门槛（定义"什么算调好了"）**

这一节是本文件最有价值的部分。**以下区间不满足，就不该进预制作：**

| 指标 | 目标区间 | 不满足说明 |
| --- | --- | --- |
| 勤奋策略 `hold_rate` | **≥ 80%** | 太苛刻，玩家学不会 |
| 偷懒策略 `hold_rate` | **30%–50%** | 太宽松=决策无意义；太低=惩罚过重 |
| 莽夫策略 `hold_rate` | **≤ 15%** | 不防守也能过，玩法崩塌 |
| 勤奋 − 偷懒 差值 | **≥ 30 个百分点** | **低于此值 = 经营决策无价值，玩法无深度** |
| `nights_per_season` | **1.0–2.0** | 高于 2 变纯塔防；低于 1 威胁感消失 |
| 地力在 4 季末的平均值 | **≥ 25** | 低于此说明地力损耗过快，玩家被逼到只能休耕 |
| 勤奋策略通关率 | **40%–70%** | 太高没挑战，太低第一款游戏太劝退 |

**R7 · 与字表设计的联动**

工具的另一个用途：**换 60 字白名单，重跑，看指标**。

- 字表加 10 个防御字 → `hold_rate` 应显著上升；若无变化，说明这些字是废件。
- 字表加 10 个产出字 → `coin_curve` 上升；若地力曲线塌陷，说明经济过强。
- **用它来验"每个字都有存在意义"**，这是 60 字表设计阶段最有用的反馈。

### 状态和转换

M4 自身无状态。每次运行：构建初始 `FarmState` → 循环 `RoundStart/策略决策/EndRound` → 输出报告。

### 与其他系统的交互

| 系统 | 方向 | 接口 | 所有权 |
| --- | --- | --- | --- |
| F2 步进 | 上游 | `Execute` + `ReplayHash` | F2 拥有 |
| F3 状态层 | 上游 | 构造与读取 `FarmState` | F3 拥有 |
| F1 字表 | 上游 | 读 JSON（不经引擎） | F1 拥有 |
| 全部玩法系统 | 上游 | 通过命令驱动，不自建捷径 | 各系统拥有规则 |
| CI | 下游 | 作为门禁任务 | — |

## 公式

### 4.1 报告汇总

```
hold_rate       = 全守祟夜数 / 祟夜总数
avg_soil        = 各季末全田地力均值再取平均
depth_gap       = hold_rate(勤奋) − hold_rate(偷懒)
```

### 4.2 运行预算

```
单局：约 28 回合 × 7 步 ≈ 200 步，纯逻辑 < 10 ms
100 局：< 1 s（不含 IO）
```

## 边缘情况

| # | 情况 | 处理 |
| --- | --- | --- |
| E1 | 策略在无合法命令时陷入死循环 | 强制 `EndRoundEarly`，并记录"策略卡死"计数（这个数字本身是设计信号） |
| E2 | 字表 JSON 缺失/非法 | 直接报错退出，不静默跑空表 |
| E3 | 同一 seed 两次运行 hash 不同 | **视为严重缺陷**（有静态随机源或哈希不稳定），CI 直接红 |
| E4 | 工具引用了 Godot 程序集 | 编译期拦截（csproj 不引用），这是架构守卫 |
| E5 | 100 局里出现 1 局异常崩溃 | 输出该局的完整命令日志到 `crash/`，便于逐条重放 |

## 验收标准

- [ ] **A1** 不启动 Godot 可编译并运行（`dotnet run`）
- [ ] **A2** csproj 不引用任何 Godot 程序集（架构守卫）
- [ ] **A3** 同 `(seed, strategy, charTable)` 的 `final_hash` 两次运行完全一致（E3）
- [ ] **A4** 三种策略的 `hold_rate` 差距满足 R6 的门槛
- [ ] **A5** 100 局运行 < 10 s（含 IO）
- [ ] **A6** 输出 CSV + Markdown 两份报告
- [ ] **A7** 异常局能导出完整命令日志并逐条重放（E5）
