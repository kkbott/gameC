# F2 · 确定性步进与命令层（Deterministic Step & Command）

> **状态**: 设计中 · v0.1
> **作者**: 创意总监 + agent
> **最后更新**: 2026-11-17
> **实现支柱**: 无直接玩法支柱，服务于 P4「一季不回头」的**可信性**（回不去，所以每一步都要算得清）
> **系统层级**: 基础层 / MVP / 设计顺序第 3
> **上游**: 无

---

## 概述

F2 是**所有规则推进的唯一通道**。它规定四件事：状态只能在什么时候变、玩家用什么方式请求变化、随机数从哪来、两次相同输入会不会得到相同结果。

它是 §5.4 四条架构约束里第 2 条的载体：**确定性步进 + 命令式输入**。没有它，M4 平衡工具跑不了批量回归、bug 无法复现、将来的联机要推倒重写。

**本作是回合制，不是实时制。** 一条农事轮由玩家驱动，不靠时钟。所以"tick"在这里指**逻辑步**，不是帧：

```
逻辑步 Step   = 一次命令被校验并应用（原子、可回放）
回合 Round    = 若干 Step + 一次结算 Step
夜 Night      = 一次祟夜结算 Step（无玩家操作）
季 Season     = 6–8 回合 + 0–2 夜 + 一次季末结算 Step
```

> **v0.1 修订说明**：系统索引原描述为"固定步长推进（30Hz 类实时 tick）"。设计 F3 时确认玩法是回合制的——布字、结算、祟夜都是离散事件，没有需要实时推进的量。改为步进制后：M4 回归只需重放命令日志；存档只需存命令日志 + 初始种子即可完整复现；联机同步量极小。

---

## 玩家幻想

玩家感觉不到 F2 的存在，但它的缺席会被立刻察觉：**如果同样的操作有时成功有时失败，玩家就不会相信这片地**。

这个系统服务的是一种很朴素的感觉——**"我做了什么，它就发生什么"**。支柱 P4「一季不回头」之所以能成立，前提就是每一步都可归因、不可篡改。

## 详细设计

### 核心规则

**R1 · 单一变更入口**

`FarmState` 只能通过 `Execute(command)` 改变。禁止任何子系统直接写字段。

```
外部（UI / 输入 / AI / 回放）  →  命令对象  →  Step 队列  →  Apply(FarmState)
```

**R2 · 命令分两阶段：先校验，后应用**

```csharp
public interface ICommand
{
    // 阶段 1：只读校验。返回 null 表示可执行。
    Rejection? Validate(FarmState state, StepContext ctx);

    // 阶段 2：改变状态。只允许写 FarmState 与 ctx 提供的 RNG。
    void Apply(FarmState state, StepContext ctx);
}
```

- `Validate` **必须无副作用**（不扣资源、不改状态）。
- `Apply` 只能读写传入的 `state` 与 `ctx`，**不得访问任何静态/单例**。
- 校验失败的命令**不进入 Step 队列**，只抛拒绝事件，状态零变化（对应 C3 的 `locked`/`occupied`/`not_enough_parts`）。

**R3 · Step 是原子的**

一个 Step 内要么全部生效，要么全部不生效。做法：`Apply` 前对受影响实体做快照，抛异常则回滚 + 记录（开发期直接断言失败，发行期回滚并跳过）。

**R4 · 唯一随机源**

```csharp
public sealed class DeterministicRng
{
    private ulong _s;                       // PCG/xorshift 状态，进存档
    public DeterministicRng(ulong seed);
    public int Range(int minInclusive, int maxExclusive);
    public ulong Snapshot();
    public void Restore(ulong s);
}
```

- 全部随机（发牌、字灵台词选取、祟的路径选择）**只能**从这里取。
- **禁止** `GD.Randi` / `RandomNumberGenerator`、`System.Random`、`Guid.NewGuid`、时间戳参与任何判定。
- RNG 状态属于 `FarmState`，随存档走。

**R5 · 结算顺序固定**

同一 Step 内多个效果同时触发时，按**固定优先级**结算，不得依赖集合遍历顺序：

```
1. 命令本身的效果（布字/清祟）
2. 地力与产出结算
3. 祟气重算
4. 祟夜触发判定
5. 祟夜结算（若触发）
6. 村民去留判定
7. 季末判定
```

> 为什么写死：C3 E7 要求"同一 tick 合字与摧毁按固定顺序结算"，那条规则的正确性完全依赖这张表。

**R6 · 可回放**

`(初始 FarmState 快照, 种子, 命令日志)` 三者确定整局。提供：

```csharp
string ReplayHash(FarmState s);   // 规范化序列化后 FNV-1a，64 位
```

同输入两次运行 hash 必须相同。这是 M4 与将来联机校验的共同地基。

**R7 · 视图只读 + 事件订阅**

表现层不得反写状态。状态变化通过事件通报：

```
CharComposed, ComposeFailed, SuiCleared, RoundEnded,
NightResolved, VillagerLeft, SeasonEnded, CommandRejected
```

事件只在 Step 结束后批量派发（不中断 Step 原子性）。

### 状态和转换

F2 自身无玩法状态。它维护的**运行期**对象：

| 对象 | 生命周期 | 是否进存档 |
| --- | --- | --- |
| Step 队列 | 单次 `Dispatch` 内 | 否 |
| 命令日志 | 整局（可裁剪到最近 N 回合用于调试） | 是（可选，发行版默认不存） |
| 回滚快照 | 单次 `Apply` 内 | 否 |
| RNG 状态 | 整局 | **是** |

### 与其他系统的交互

| 系统 | 方向 | 接口 | 所有权 |
| --- | --- | --- | --- |
| F3 状态层 | 上游（被操作对象） | `Execute(ICommand) -> StepResult` | F3 拥有数据，F2 拥有变更通道 |
| 所有玩法系统（C1–C7、G1–G5） | 下游 | 各自实现 `ICommand`；禁止自行改状态 | 各系统拥有自己的命令类型 |
| M4 平衡工具 | 下游 | 读命令日志 + 种子做重放 | F2 提供 `ReplayHash` |
| P1 输入映射 | 下游 | 把手势翻译成命令对象 | P1 拥有映射，F2 拥有执行 |
| P7 场景流程 | 下游 | 发起 `StartSeason` / `EndSeason` 等流程命令 | F2 不感知"场景"概念 |

## 公式

### 4.1 定点数约束

```
所有判定量用整数或 Q16.16 定点，禁止 float/double 参与判定
显示层可用浮点（渲染插值），但不得回写
```

理由：浮点的跨平台一致性不足，M4 与将来的联机都要求 bit-exact 复现。

### 4.2 状态哈希

```
hash = FNV1a64( canonicalJson(state) )
canonicalJson = 键按字典序、数字用整数或定点字符串、枚举用字符串名、集合按稳定键排序
```

### 4.3 一局的时间预算（逻辑步，非帧）

```
1 回合 ≈ 6 次布字 Step + 1 次结算 Step = 7 步
1 季   = 6–8 回合 + 0–2 夜 + 1 季末 = 约 50–65 步
1 局   = 4 季 ≈ 220–260 步
```

## 边缘情况

| # | 情况 | 处理 |
| --- | --- | --- |
| E1 | 同一 Step 内两条命令改同一田块 | 队列**串行**应用，第二条的 `Validate` 看到第一条的结果，自然被拒 |
| E2 | `Apply` 抛异常 | 开发期断言崩溃并打印命令；发行期回滚该 Step、记日志、跳过，不连锁崩溃 |
| E3 | 回放时命令因规则变更而不再合法 | 标记该局回放为 `stale_version`，禁止用于校验，仅作调试参考 |
| E4 | 命令日志被裁剪后无法完整回放 | 裁剪只影响调试；完整性校验用"每季末 hash 快照"而非全量日志 |
| E5 | 多平台浮点差异 | 通过 §4.1 定点数约束从根上消除，不做事后补偿 |
| E6 | 事件监听者在派发中再发命令 | **禁止**：派发期间 `Execute` 入队延后到下一 Step，防重入 |

## 调整旋钮

| 旋钮 | 初值 | 说明 |
| --- | --- | --- |
| 命令日志保留回合数 | 3 | 调高便于调试，调高占存档体积 |
| 释放期是否严格断言 | 开（开发期） | 发行期改为回滚+日志 |
| 每季 hash 快照数 | 1（季末） | 调高更易定位分歧点，代价是存档变大 |

无。F2 是纯逻辑基础设施。

无直接 UI。唯一间接要求：命令被拒绝时必须有**轻量可见反馈**（对应 C3 的拒绝事件），否则玩家会以为点击没生效。

## 验收标准

- [ ] **A1** 静态检查：`TianziGe.Sim` 程序集内 **0 处** `using Godot`；`dotnet test` 编译并通过
- [ ] **A2** 同一初始状态 + 同一命令序列，跑两次 `ReplayHash` 相同
- [ ] **A3** 同一初始状态 + 同一种子，发牌 1000 次序列完全一致（跨平台 CI 验证）
- [ ] **A4** `Validate` 无副作用：调用 1000 次后状态 hash 不变
- [ ] **A5** 校验失败的命令不改变状态（hash 不变）且产生 `CommandRejected` 事件
- [ ] **A6** `Apply` 抛异常时状态回滚到 Step 前（hash 恢复）
- [ ] **A7** 结算顺序符合 R5：构造"合字成功 + 祟夜摧毁同田"的用例，结果可复现
- [ ] **A8** 事件派发期间再发命令会延迟到下一 Step，不破坏原子性
- [ ] **A9** 全流程无 `float` 参与判定（静态检查：Sim 层无 `float`/`double` 字段）
- [ ] **A10** 一季 50–65 步的最坏情况结算总耗时 < 20ms
