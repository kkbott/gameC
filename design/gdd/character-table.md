# F1 · 字表数据（Character Table）

> **状态**: 设计中 · v0.2（已按 design-review 修订 6 项）
> **作者**: 创意总监 + agent
> **最后更新**: 2026-11-17
> **实现支柱**: P1 字即是手（主）、P2 认得就是得到
> **系统层级**: 基础层 / MVP / 设计顺序第 1

---

## 概述

字表是这个游戏的**唯一规则数据源**：一张手写的白名单，每个条目说明「哪两个部件能组成哪个字，这个字对土地做什么」。

它是所有玩法系统的上游——合字校验查它，字效派发读它，偏旁发牌按它反推，平衡工具直接跑它。**没有字表就没有游戏**；字表改一个字段，六个下游系统跟着返工。所以它是本项目最大的瓶颈系统，也是最先要定死的东西。

**数据形态**：JSON 为源，ScriptableObject 仅为运行时包装。原因见 §6.1。

---

## 玩家幻想

玩家不"操作字表"，玩家感受到的是：**我的字库在变厚，而这片地跟着变。**

- 第一次见到「禾 + 火 = 秋」，玩家应有一瞬间的**恍然**——不是"我查到了"，而是"对啊，秋天就是禾熟了、被收割的火气烘过"。
- 到第三季，玩家脑海里应该长出一张**自己的字网**：他知道"氵"在手上时该等什么，知道哪几个字配他的田型。这时他不再试错，他在**写**。
- 反幻想（明确不要）：玩家不该感觉自己在一本字典里找答案，也不该感觉自己在中奖机器前抽卡。

## 详细设计

### 核心规则

**R1 · 条目结构**

每个字表条目是一个 JSON 对象：

```json
{
  "id": "qiu",
  "char": "秋",
  "components": ["禾", "火"],
  "category": "produce",
  "template": "all_ripen",
  "tier": 2,
  "duration": { "kind": "instant" },
  "seasonAffinity": ["秋"],
  "perSeasonLimit": 1,
  "flavor": "一叶落，天下秋",
  "desc": "全场作物立即成熟"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | ascii slug | **稳定主键**，存档只存它。改字不改 id |
| `char` | string | 结果字，展示用；可随版本改 |
| `components` | `[a, b]` | **无序二元组**（见 R2） |
| `category` | enum | `produce` / `soil` / `defense` / `relation`，**同时决定主导属性**（见 R8） |
| `template` | enum | 效果模板 id，见 R5 |
| `tier` | 1–3 | 阶，**只放大主导项**（见 R8） |
| `duration` | object | 结构化，见下 |
| `seasonAffinity` | string[] | 季节亲和，命中则加成（语义见 §4.5） |
| `perSeasonLimit` | int / null | 每季可用次数，`null` = 不限 |
| `flavor` | string | 字灵短句 / 农书条目语，一句 |
| `desc` | string | 一句话效果说明，必须"看图说话" |

> **⚠️ 已删除 `battleWill` 字段**（v0.2 修订）。原字段为手填值，与 §4.1 的推导公式冲突（示例中 `秋` 手填 1，而 tier=2 推导为 2），C7 实现时必然选错。**战意改为纯推导量，不再进数据。**
>
> `duration` 采用结构化编码而非字符串：`{"kind":"instant"}` / `{"kind":"season"}` / `{"kind":"rounds","rounds":3}`。字符串 `"rounds:N"` 无法被 schema 校验，且解析易错。

**R2 · 校验规则（无序匹配）**

1. 收到部件对 `(x, y)`。
2. 规范化：按 **`glyphId`**（不是 Unicode 码位）排序，得到唯一的无序键。
3. 查索引表 `unorderedIndex`。
4. 返回命中条目或 `null`。
5. **`Lookup` 是纯查表**：不读存档、不读《农书》状态、不产生副作用。

> **已决议**：部件顺序**不敏感**。`禾+火` 与 `火+禾` 等价。第一款游戏以容错优先；顺序敏感的玩法留作后期可选深度，不进 MVP。

> **⚠️ v0.2 修订**：原第 5 步把"《农书》已收录则免检"写进了 `Lookup`，等于让 F1 反向依赖 G1，与 §6.2「上游：无」自相矛盾。**免检判断归 C3**：C3 在调用 `Lookup` 之前先查农书，命中则跳过校验。F1 不知道农书存在。

**R3 · 部件登记表**

部件不是字表的一部分，而是它的索引：

```json
{ "glyph": "禾", "glyphId": 7, "kind": "semantic", "family": "cereal", "targets": ["qiu", "miao", "sui"] }
```

`targets` 记录**这个部件能参与组成哪些字**，是可达性发牌的唯一依据（R4）。`family` 用于同族加成（§4.2）。`glyphId` 是整数主键，用于构造无序键（见 A15）。

**R4 · 可达性发牌（系统最关键的防坑规则）**

手牌容量 `H`（初值 5）。每次补牌：

- 权重抽样：`w(部件) = 1 + λ × 可达目标数`
  - `可达目标数` = 该部件与当前手牌/场上已存在部件能立即凑成的字数量
- **硬约束**：任何时刻手牌中必须存在**至少 1 个可立即成字**的组合。若抽样后不满足，强制替换一张为匹配部件。
- 目标失败率 `f*`（初值 **0.20**，安全区间 0.15–0.25）。

> 为什么这条比数值都重要：若偏旁池 40 个、白名单 60 字而发牌纯随机，单次配对命中率不足 1%。玩家会连续失败十几次然后关掉游戏。**合字的爽感来自"我猜对了"，不能来自"我抽中了"。**

> **λ 标定流程**（v0.2 补充，原文档只说"由 f* 反解"而没有流程，实现者会卡住）：
> 1. 固定字表与部件池，写一个无渲染的模拟脚本。
> 2. 用二分法在 `λ ∈ [0, 20]` 内迭代，每轮跑 1000 次发牌 + 配对。
> 3. 记录实测失败率，取最接近 `f*` 的 λ，要求 `|实测 − f*| ≤ 0.02`。
> 4. 把 λ 写回配置并锁定；字表或部件池变动超过 10% 时重跑标定。

**R5 · 效果模板（4 类 / 13 模板）**

| 类别 | 模板 id | 效果 | 典型 duration |
| --- | --- | --- | --- |
| produce | `single_ripen` | 单块田立即成熟 | instant |
| produce | `all_ripen` | 全场立即成熟（受 perSeasonLimit 限制） | instant |
| produce | `adjacent_boost` | 相邻田产出 +50% | season |
| produce | `sustained_yield` | 之后 N 轮每轮产出 | rounds:N |
| produce | `clear_sui` | 清除全部祟字并释放其占用格 | instant |
| soil | `fallow_restore` | 本季不产，地力回满 | season |
| soil | `soil_guard` | 本块田地力不被祟夜削减 | season |
| defense | `ward_wave` | 挡下祟夜第一波 | rounds:1 |
| defense | `reveal_stealth` | 显形隐身的祟 | season |
| defense | `will_boost` | 本块田战意 +2 | season |
| relation | `villager_favor` | 村民好感 +1 | instant |
| relation | `hand_growth` | 下一轮手牌 +1 | rounds:1 |
| relation | `spirit_affinity` | 字灵亲密度 +1 | instant |

> 表中 duration 为简写，实际 JSON 一律结构化：`instant` → `{"kind":"instant"}`，`season` → `{"kind":"season"}`，`rounds:N` → `{"kind":"rounds","rounds":N}`。

**已决议**：采用 4 类 + 每类 2–3 个效果模板（13 个），而非纯 4 类。理由是 60 个字塞进 4 类会退化成同义词表，玩家无法判断"这个坑该写哪个字"。

**R6 · 阶（tier）与稀有度**

`tier` 由**部件稀有度之和**决定，设计师手填但需符合下表：

| tier | 判据 | 示例 |
| --- | --- | --- |
| 1 | 两个部件都是高频日常部件 | 苗（艹+田）、早（日+十） |
| 2 | 含一个中频部件 | 秋（禾+火）、江（氵+工） |
| 3 | 含一个低频部件，或双同部件 | 炎（火+火）、明（日+月） |

**R7 · 首批 60 字的选取原则**

- 只用小学阶段的常用会意 / 形声字；**生僻字一律不进**。
- 效果必须**看图说话**：识字的人读第三遍不用看说明就该懂。
- 类别覆盖：每类 ≥ 10 字（4 类 × 10 = 40，余 20 字自由分配）。
- 阶分布：tier1 ≥ 30、tier2 ≈ 20、tier3 ≈ 10（前期要能玩）。
- 季节亲和分布均衡，四季各 ≥ 8 字。
- **禁止**：只靠读音才能懂的字、一字多解的字、可作为人名/地名的专有字。

**已决议**：按"一看就懂"筛选，而非按部首聚类。宁愿 60 字里有 20 个意思相近，也不要 1 个需要查字典。

**R8 · 主导属性制（tier 只放大主导项）**

`category` 决定这个字的主宰赛道，`tier` **只放大主导项**，非主导项固定为低值：

| category | 主导项 | 主导项随 tier 放大 | 非主导项（固定） |
| --- | --- | --- | --- |
| produce 产出 | 产出系数 | `mainYield[tier]` | 战意 = `SUB_WILL` |
| defense 防御 | 战意 | `mainWill[tier]` | 产出系数 = `SUB_YIELD` |
| soil 地力 | 地力恢复量 | `mainSoil[tier]` = {1:20, 2:35, 3:55} | 战意 `SUB_WILL` / 产出 `SUB_YIELD` |
| relation 关系 | 关系收益 | `mainRel[tier]` = {1:1, 2:2, 3:3} | 战意 `SUB_WILL` / 产出 `SUB_YIELD` |

> **v0.2 修订理由**（原设计为 tier 同时放大战意与产出）：若两项同时随 tier 上升，tier1 的字在**两条赛道都最弱**，玩家只追 tier3——60 个字里那 30 个 tier1 会变成废件，正好违背"内容靠规则组合而非手工内容"的立项理由。主导属性制让低阶字在自己的赛道上依然可用。

### 状态和转换

字表本身是**只读静态数据**，无运行时状态。但每个条目有"对玩家可见性"的生命周期：

| 状态 | 含义 | 进入条件 | 离开条件 |
| --- | --- | --- | --- |
| 未知 | 玩家从未组成过 | 初始 | 首次成功合成 |
| 已悟 | 组成过，入《农书》，免检可用 | 首次成功合成 | — |
| 已用 | 本季已用完次数（`perSeasonLimit`） | 次数耗尽 | 季末重置 |

```
未知 --[成功合成]--> 已悟 --[perSeasonLimit 耗尽]--> 已用 --[季末]--> 已悟
```

> 注：本表记录的是 **F1 与 G1 之间的契约**，状态本体归 G1《农书》所有。**免检的判断权在 C3**（见 R2 修订说明）。G1 设计时必须回来核对本表。

### 与其他系统的交互

| 系统 | 方向 | 接口 | 所有权 |
| --- | --- | --- | --- |
| C3 合字校验 | 下游 | `Lookup(glyphId a, glyphId b) -> CharDef?`（纯查表） | 本系统提供数据；农书免检由 C3 在调用前判断 |
| C2 偏旁池 | 下游 | 读 `componentRegistry.targets` 做可达性发牌 | 本系统提供 targets 与 `glyphId` |
| C4 字效 | 下游 | 读 `category`（主导属性）+ `template` + `tier` 派发效果 | 本系统只声明模板，不实现效果 |
| F3 状态层 | 下游 | 字表**不进存档**；存档只存 `id` 列表 | 本系统只读 |
| M4 平衡工具 | 下游 | 直接读 JSON，不经 Unity | 本系统必须保持纯数据 |
| P3 农书 UI | 下游 | 读 `flavor` / `desc` / `char` | 本系统提供文案字段 |
| C7 祟夜 | 下游 | 读推导出的 `battleWill_eff` 汇总防力 `D`；**不提供** `seasonCoef` | 公式在 C7，本系统只给单字战意 |

## 公式

### 4.1 战意值（供 C7 汇总）

```
isDefense(c)        = (c.category == defense)

battleWill_base(c)  = isDefense(c) ? mainWill[c.tier] : SUB_WILL
battleWill_eff(c)   = battleWill_base(c) + affinityBonus(c) − repeatPenalty(c)

mainWill           = { 1: 1, 2: 2, 3: 3 }
SUB_WILL           = 0.5
affinityBonus(c)   = (currentSeason ∈ c.seasonAffinity) ? +1 : 0
repeatPenalty(c)   = 0.3 × (同 id 已在本季田中的块数 − 1)，下限 0
```

> `affinityBonus` 与 C7 的「季相系数」是两个不同的东西，**禁止相乘两次**。裁决见 §4.5。

### 4.2 产出系数（供 C5 结算）

```
isProduce(c)     = (c.category == produce)

yieldMul_base(c) = isProduce(c) ? mainYield[c.tier] : SUB_YIELD
yieldMul_eff(c)  = yieldMul_base(c) × (1 + 0.2 × sameFamilyCount)

mainYield        = { 1: 1.0, 2: 1.6, 3: 2.4 }
SUB_YIELD        = 0.6
sameFamilyCount  = 场上与任一部件的 family 相同的部件数，**上限 2**（→ 加成上限 +40%）
```

> 上限说明：一块田只有 2 个部件，同族加成实际封顶 +40%。该幅度是旋钮（见 §7），需要试玩确认是否够让"成族布局"有吸引力。

### 4.3 可达性目标（供 C2 发牌）

```
可达目标数(部件) = |{ t ∈ targets(部件) : 另一半部件 ∈ 手牌 ∪ 场上 }|
w(部件)         = 1 + λ × 可达目标数
```

λ 的标定流程见 R4 的第二段引注。本系统规定目标值 `f*`，C2 负责实现与标定。

### 4.4 祟气输入（供 C6 使用）

```
suiCharCount = 场上祟字占用的田块数
```

本系统只定义"失败即生成祟字"这一事实；`ΔQ += 3 × suiCharCount` 由 C6 拥有。

### 4.5 季节语义正交（裁决 Q5）

两个都叫"季节"的量必须区分，实现时**不得相乘两次**：

| 名称 | 归属 | 作用对象 | 语义 |
| --- | --- | --- | --- |
| `affinityBonus` 字缘加成 | **F1（本系统）** | 单个字 | 这个字与该季节是否投缘（个别字 +1） |
| `seasonCoef` 季相系数 | **C7 崇夜** | 整条防力 | 全局难度曲线（春/夏/秋/冬） |

**规定**：C7 的防力按
```
D = (Σ battleWill_eff) × (1 + 0.1 × (村民数 − 5)) × seasonCoef
```
计算，其中 `seasonCoef` **只整体乘一次**，不得再对单个字重复施加。

## 边缘情况

| # | 情况 | 处理 |
| --- | --- | --- |
| E1 | 两个部件相同（火 + 火 = 炎） | **允许**。`components[0] == components[1]` 是合法条目，按普通条目查表 |
| E2 | 同一个字写进多块田 | 允许。`yieldMul_eff` 正常，但 `battleWill_eff` 走 `repeatPenalty` 递减 |
| E3 | 玩家拼出真实存在的汉字，但不在白名单 | **一律当祟字**。这是设计决定不是技术限制：玩家学的是《农书》，不是字典 |
| E4 | 手牌全满但无任何有效组合 | 硬约束发牌兜底（R4）；若仍失败，触发"糊字"保底（随机有效弱字，见概念 §7） |
| E5 | 字效持续期内该田被祟夜摧毁 | 效果**立即终止**，不残留、不迁移 |
| E6 | 版本更新后旧存档里的 `id` 已删除 | 存档加载时跳过并记录警告，不崩溃；`char` 改名不受影响（id 稳定） |
| E7 | 祟夜中玩家尝试合字 | 字格锁定，命令被拒；返回"字灵嘲讽"事件供 P3 播放 |
| E8 | `perSeasonLimit` 耗尽后仍尝试复用 | 允许合成但不生效，返还部件并提示"这个字今年用过了" |
| E9 | 同一无序部件对被两条记录命中 | **数据错误**。构建期校验必须拦截（见 A3） |
| E10 | 部件池里存在"死部件"（不参与任何字） | **数据错误**。构建期校验拦截（见 A4） |
| E11 | 非主导类别的字被放进祟夜防线 | 允许，但战意只有 `SUB_WILL`（0.5）。这是**有意的**：拿产出字去守夜是玩家的错误决策，应有代价 |

## 依赖关系

### 6.1 为什么必须是 JSON 源（架构约束）

`M4 平衡回归工具` 需要**脱离 Unity** 批量跑季（§5.4 第 1 条的验收方式）。`.asset` 文件依赖 Unity 序列化，Unity 之外读不了。因此：

- **源文件**：`Data/char-table.json` + `Data/component-registry.json`（纯文本、可 diff、可脚本校验）
- **运行时**：`CharTableSO`（ScriptableObject）在 Editor 导入时读取 JSON 并包装为只读字典
- **禁止**：在 SO 里手改数值（会被下次导入覆盖），改数只改 JSON

### 6.2 上下游

| 方向 | 系统 | 契约性质 |
| --- | --- | --- |
| 上游 | **无** | 它是根系统。v0.2 起确认：连《农书》也不是它的上游（免检权已移交 C3） |
| 下游 | C3 合字校验、C2 偏旁池、C4 字效、F3 状态层、M4 平衡工具、P3 农书 UI、C7 祟夜 | **全部是硬依赖**：缺字表这些系统无法运行 |

**双向一致性检查**：C3 / C2 / C4 / C7 的 GDD 必须各自列出"依赖 F1"并引用本文件的接口签名。任一系统未列，视为文档缺陷。

## 调整旋钮

| 旋钮 | 初值 | 安全范围 | 太高会怎样 | 太低会怎样 |
| --- | --- | --- | --- | --- |
| 手牌容量 `H` | 5 | 3–8 | 选择过载，玩家不做判断只乱塞 | 无解可写，节奏卡死 |
| 目标失败率 `f*` | 0.20 | 0.15–0.25 | 挫败感压过爽感，玩家弃游 | 没有悬念，合字变成无脑拼图 |
| 发牌权重 `λ` | 由标定得出 | 0–20 | 手牌过度"喂答案"，探索感消失 | 失败率失控，等同纯随机 |
| `mainWill` | 1 / 2 / 3 | 1–4 | 防御字压制一切，产出字无人用 | 阶失去意义 |
| `mainYield` | 1.0 / 1.6 / 2.4 | 1.0–3.0 | 经济崩盘，滚雪球失控 | 玩家没动力追高阶字 |
| `SUB_WILL` 非防御字战意 | 0.5 | 0.2–0.8 | 产出字也能守夜，主导属性制失效 | 产出字完全没有防守价值，逼玩家两套阵容 |
| `SUB_YIELD` 非产出字产出 | 0.6 | 0.3–0.8 | 防御字也能赚钱，无需布局取舍 | 防御字长期纯亏损，玩家不敢布防 |
| `sameFamilyCount` 系数 | 0.2（上限 2） | 0.1–0.3 | 成族布局唯一解，其他布局全废 | 同族概念形同虚设 |
| `perSeasonLimit` | 秋=1、其余 null | 1–3 | 强字可反复刷，退化策略 | 强字变废件 |
| `repeatPenalty` | 0.3 | 0–0.5 | 重复即废，逼迫玩家乱写 | 一招通关（叠同一个字） |
| 白名单总字数 | 60（MVP）→ 300–500（发行） | 60–500 | 超出单人设计产能，字义开始凑数 | 内容量不足，后期无探索空间 |
| `affinityBonus` 字缘加成 | +1 | 0–2 | 季节强制换阵容，玩家反感 | 季节亲和形同虚设 |

**旋钮联动**：`f*` 调高必须同时调低 `H`（否则失败率上升但手牌过剩，体验反而更差）；`白名单总字数` 上升会自然降低命中率，需要同步上调 λ 或 `H`；`SUB_WILL` 与 `SUB_YIELD` 一起调，否则两套阵容的成本失衡。

## 视觉/音频需求

- 合字成功：两部件墨迹**合流**成一字（字形变形动画），并非淡入淡出。
- 合字失败：两部件**溅开成墨团**（祟字），带一声低沉的闷响。
- 字落入田：落纸的顿感 + 田块轻微凹陷。
- 农书翻页：宣纸摩擦声。
- 细则留给 P5 水墨 VFX / P6 音频，本系统只规定"合/不合"两种反馈必须有明确区分，不得只靠颜色。

## UI需求

- 田块上悬浮字效**预览**（拖动时显示"若放到这里会发生什么"）。
- 字条展示：`char` + `components` + `desc` + `flavor`，竖排排版交 P3/P4。
- 已用尽的字（`perSeasonLimit`）需有可见的灰化状态。
- 非主导类别在祟夜中应显示其低战意（如灰化的战意数值），让玩家知道自己布错了阵。

## 验收标准

**数据完整性（构建期自动校验，不启动 Unity）**

- [ ] **A1** JSON 可被脚本解析，条目数 = 白名单声明数（MVP = 60）
- [ ] **A2** 所有 `template` / `category` / `duration.kind` 值在枚举范围内
- [ ] **A3** 无重复无序部件对（按 `glyphId` 排序后比较；`禾,火` 与 `火,禾` 只允许存在一条）
- [ ] **A4** 无死部件：`componentRegistry` 中每个部件至少出现在 2 个条目中
- [ ] **A5** 所有 `id` 唯一且为 ascii slug；`glyphId` 唯一且为正整数
- [ ] **A6** 类别覆盖：produce / soil / defense / relation 各 ≥ 1（MVP），发行版各 ≥ 10
- [ ] **A7** 阶分布：tier1 ≥ 50% 总字数
- [ ] **A8** **不含 `battleWill` 字段**（v0.2：战意为推导量，数据里出现该字段视为错误）

**行为验证（测试跑在模拟层，无需渲染）**

- [ ] **A9** `Lookup("火","禾")` 与 `Lookup("禾","火")` 返回同一条目（无序性）
- [ ] **A10** `Lookup` 无副作用：同一输入连续调用结果一致，且不读取农书状态
- [ ] **A11** 白名单外组合返回 `null` 且上游生成祟字
- [ ] **A12** 随机 1000 次发牌，**0 次**出现"手牌中无可立即成字组合"
- [ ] **A13** 随机 1000 次配对实测失败率在 `f* ± 0.05` 内；λ 标定后误差 ≤ 0.02
- [ ] **A14** 存档往返：只序列化 `id` 列表，加载后状态一致（含已用尽的 `perSeasonLimit`）
- [ ] **A15** 删除一个 `id` 后旧存档仍能加载且不崩溃（E6）
- [ ] **A16** 主导属性制验证：`tier=1` 的 defense 字战意 ≥ `tier=3` 的 produce 字战意（低阶防守字不被高阶产出字压制）

**性能预算**

- [ ] **A17** 500 条字表的索引构建 < 5ms；`Lookup` 为 O(1) 哈希查表
- [ ] **A18** 字表加载不产生帧内 GC 峰值（键用 `(long)a.glyphId << 32 | b.glyphId` 的整数对，不做 `string` 拼接）
