# C3 · 合字校验（Compose Validation）

> **状态**: 设计中 · v0.1
> **作者**: 创意总监 + agent
> **最后更新**: 2026-11-17
> **实现支柱**: P1 字即是手（主）、P2 认得就是得到、P3 水乡会说话
> **系统层级**: 核心层 / MVP / 设计顺序第 2
> **上游**: [F1 字表](character-table.md) v0.2（已批准）

---

## 概述

合字校验是玩家把两个部件拖进田里、松手的那一瞬间：**这到底是不是一个字？**

它是整个游戏手感最集中的 0.3 秒。判定成功，田按字的意思回应你；判定失败，两团墨溅开、占掉一格、招来祟气。它不生产内容，但它决定内容**好不好玩**——F1 提供 60 个字，C3 决定玩家感受到的是"我猜对了"还是"我被抽奖机耍了"。

**它拥有的东西**：判定流程、成功/失败两个分支的后果、祟字的生成与清除、预览的可见性规则。
**它不拥有的东西**：字表数据（F1）、农书状态（G1）、效果实现（C4）、祟气数值（C6）。

---

## 玩家幻想

> **「我写对了。」**

那 0.3 秒里玩家想要的不是"系统告诉我对错"，而是**自己确认自己的判断**：

- 成功时是**恍然**，不是中奖。所以要有一个"啊，原来是这个字"的顿悟窗口，而不是直接弹数值。
- 失败时是**好笑**，不是被罚。墨团溅开、字灵在边上阴阳怪气，玩家会笑一下再重来——这直接对应支柱 P3。
- 越玩越少失败，但**不是因为失败率被系统调低了**，而是因为玩家认得多了。这是 P2「认得就是得到」在操作层的手感落点。

## 详细设计

### 核心规则

**R1 · 校验时机：松手即判，零确认**

拖拽中不判定、不预览成败；部件落到目标田的**那一帧**判定并立即给出视觉与听觉结果。没有确认按钮、没有二次询问。

> 理由：合字是高频动作（一轮 5–8 次）。任何确认环节都会把"顿悟"稀释成"提交表单"。

**R2 · 判定流程（C3 拥有，按序执行）**

```
1. 字格锁定期（祟夜）？          → 拒绝，不消耗任何资源，抛 "locked" 事件
2. 目标田已被占用（有字/有祟字）？ → 拒绝，不消耗，抛 "occupied" 事件
3. 手牌少于 2 张？               → 拒绝，不消耗，抛 "not_enough_parts" 事件
4. 查《农书》（G1 只读）：`IsLearned(glyphIdA, glyphIdB)` 命中？
      → **免检分支**：字已确定，跳过第 5 步查表，直接进「成功分支」
5. 调 F1.Lookup(glyphIdA, glyphIdB)
      命中  → 成功分支
      未命中 → 失败分支
```

关键约束（来自 F1 v0.2 的契约修正）：
- `Lookup` 是**纯查表**，它不知道农书存在。**免检查询由 C3 在第 4 步自己做**，绝不下沉到 F1。
- 前 3 步的拒绝**不消耗任何资源**。玩家的误操作不该有成本，判断错误才该有。
- **农书必须以「部件对」为键索引**（`glyphIdA, glyphIdB`），不能只以字 `id` 为键。否则第 4 步必须先 `Lookup` 才能拿到 `id`，"免检"就成了一句空话——这是一条硬契约，直接影响 G1 的数据结构（见 §6 依赖关系）。

**R3 · 成功分支**

1. 在该田创建字实例（保存 `id` + 生效起止轮次）。
2. 消耗手牌中的两个部件。
3. 若该 `id` 首次被组成：写入《农书》（G1），并播放「顿悟」反馈（字义展开、字灵短句）。
4. 交给 C4 派发效果（C3 不实现任何效果）。
5. 视觉：两部件墨迹**合流**成一字（P5）。

**R4 · 失败分支**

1. **两个部件都消耗**（不返还）。
2. 在目标田生成一个**祟字**：占据该字格、不产出、不可被覆盖。
3. 祟字计数 +1（`suiCharCount`）。祟气数值由 C6 按 `ΔQ += 3 × suiCharCount` 自行重算——**C3 不直接修改祟气**。
4. 视觉：两团墨**溅开**并凝成墨团（P5）；音频：低闷响（P6）。
5. 该失败组合**不写入《农书》**，也不写入任何历史记录。

> **为什么"双消耗 + 占格"**：这是我在三个方案里选的——
> - 只消耗不占格 → 惩罚太轻，玩家会无脑试错，20% 失败率形同虚设。
> - 占格不消耗 → 部件可回收，等于没惩罚。
> - **双消耗 + 占格** → 惩罚落在**空间**上（田格是核心稀缺资源），与概念里 `suiCharCount → 祟气` 的链路天然咬合，不需要新资源。

**R5 · 祟字的清除（提供主动权，不给死锁）**

祟字有两条清除路径：

| 路径 | 成本 | 说明 |
| --- | --- | --- |
| 铜钱清除 | 3 铜钱 / 个（C5 扣款） | 随时可用，最直接的止损 |
| 字效清除 | 写 `炎`（火+火，`template: clear_sui`） | 一次清全场，成本是两个部件 |

**兜底规则（防死锁）**：若铜钱 < 3 且手牌里凑不出 `炎`，则**下一次成功合字自动额外清除一个祟字**。玩家永远有出路。

**R6 · 预览的可见性（服务 P2 的核心设计）**

拖动时，目标田上显示预览，但**只对《农书》里已收录的组合显示成败**：

| 情况 | 预览显示 |
| --- | --- |
| 该组合已在农书里 | 「你写过这个字」→ 显示字与效果预览 |
| 该组合不在农书里 | 「没写过」→ **不显示会成功还是会失败** |

> 这一条是"认得就是得到"在 UI 上的兑现：**学会一个字 = 换来一次可靠预览**。玩家会主动去记、去试，因为他知道学会的收益是可操作性的提升，而不是一个图鉴数字。

**R7 · 失败组合不记录**

失败不产生任何可查阅的记录。玩家只能靠记忆和推理。

> 代价要说清：玩家仍可以截图或纸笔穷举。但那是有成本的主动行为，且**已经在做思考**——这正是我们要的。

### 状态和转换

**田格状态**

| 状态 | 含义 | 转为空 | 转为有字 | 转为祟字 |
| --- | --- | --- | --- | --- |
| 空 | 可写 | — | 成功分支 | — |
| 有字 | 写着有效字，按 `duration` 计时 | 季末洗田 / 自毁模板 | 需先清除 | — |
| 祟字 | 占格、不产、招祟气 | 铜钱清除 / 字效清除 / 兜底 | — | — |

**一次拖拽的交互状态**

```
idle --[按住部件]--> dragging
dragging --[松手在合法田]--> judging --[命中]--> resolved_success
dragging --[松手在合法田]--> judging --[未命中]--> resolved_sui
dragging --[松手在非法目标]--> idle          (不消耗，抛事件)
resolved_* --[反馈播完]--> idle
```

## 公式

### 4.1 失败的实际代价

```
单次失败 = 2 个部件 + 1 个字格 + 3 铜钱（若立即清除祟字）

按 f* = 0.20、每轮 6 次拖拽估算：
  每轮期望失败 1.2 次
  每轮期望损失 = 2.4 部件 + 1.2 格 + 3.6 铜钱
```

**平衡意图**：单次失败**可承受**（1 格 + 2 部件），连续失败**不可承受**（3 格被占 + 6 部件蒸发）。这逼玩家停手、看图、想想，而不是继续乱试。

### 4.2 祟字清除成本

```
clearCost = 3 铜钱 / 个
兜底触发条件：铜钱 < clearCost AND 手牌无法组成 clear_sui 字
兜底效果：下一次成功合字时，额外清除 1 个祟字（不额外扣费）
```

### 4.3 预览可用性

```
canPreview(a, b) = IsLearned(a.glyphId, b.glyphId)
显示内容 = canPreview ? {字, 效果预览} : {“没写过”}
```

## 边缘情况

| # | 情况 | 处理 |
| --- | --- | --- |
| E1 | 两个部件相同（火 + 火） | 合法。与普通组合走完全相同的流程 |
| E2 | 拖到已占用田 | 拒绝，不消耗，抛 `occupied`（不自动覆盖——覆盖会误杀玩家的布局） |
| E3 | 祟夜字格锁定期间尝试合字 | 拒绝，不消耗，抛 `locked`；P3 播放字灵嘲讽 |
| E4 | 手牌只有 1 张 | 拒绝，抛 `not_enough_parts`；不发牌不惩罚 |
| E5 | 铜钱 < 3 且凑不出 `炎` | **兜底生效**：下次成功合字清 1 祟字。绝不允许无解死锁 |
| E6 | 同一组合反复失败 | 允许。祟字累积是真成本，玩家会自己学会停手 |
| E7 | 成字瞬间该田被祟夜摧毁（同一 tick） | 先结算合字再结算祟夜，顺序固定，避免随机性 |
| E8 | 存档里的祟字 | 按「田格索引 + `sui` 标记」序列化，不需要字表 `id`；加载后格子状态与祟气重算一致 |
| E9 | 玩家连续误操作（拖到非法目标） | 全部拒绝且不消耗，**不设惩罚**。误操作不是设计判断 |
| E10 | 空手牌时拖拽 | 拒绝，抛 `not_enough_parts` |

## 调整旋钮

| 旋钮 | 初值 | 安全范围 | 太高会怎样 | 太低会怎样 |
| --- | --- | --- | --- | --- |
| 失败消耗策略 | 双消耗 + 占格 | 3 种枚举（见 R4） | 惩罚过重，玩家不敢试，合字变保守 | 惩罚过轻，无脑试错，失败率形同虚设 |
| 祟字清除成本 | 3 铜钱 | 1–8 | 清不起，祟字永久占格，经济崩 | 随便清，占格惩罚消失 |
| 兜底解锁条件 | 铜钱 < 3 且无 `炎` | 固定 | 放宽则失去止损自觉 | 收紧则出现死锁 |
| 预览可见范围 | 仅已收录 | 3 档（全隐藏 / 仅已收录 / 全显示） | 全显示 → 探索感归零，变成查表游戏 | 全隐藏 → 玩家不知道为什么失败，挫败 |
| 预览是否显示失败 | 显示"没写过" | 开/关 | 显示"会失败"＝直接给答案 | 完全不提示 → 玩家不知道自己"猜过" |
| 补牌速率（每轮补 N 张） | 待 C2 定义 | 3–8 | 手牌过剩，失败代价被稀释 | **手牌枯竭，想写写不出来**——与双消耗叠加后是本系统最高风险 |

## 视觉/音频需求

- **成功**：两部件墨迹相向流动、在中心合流、笔画重组成新字，落纸有顿感；字义在旁以竖排小字展开一瞬。
- **失败**：两团墨向外溅开、凝成不规则墨团，伴随低闷响；墨团轻微呼吸（活的，不是死贴图）。
- **必须**：两种反馈在同一帧内可区分，且**不依赖颜色**（色弱可辨），靠动势与声音区分。
- 细则归 P5 / P6。

## UI需求

- 拖动时目标田显示预览框（内容受 R6 限制）。
- 拒绝类事件（`locked` / `occupied` / `not_enough_parts`）用轻提示，不用弹窗。
- 祟字上显示清除成本（3 铜钱）与"可被炎清除"的图标暗示。

## 验收标准

**行为正确性（模拟层测试，无需渲染）**

- [ ] **A1** 合法组合：成功分支执行，字实例落格，部件 −2
- [ ] **A2** 非法组合：失败分支执行，生成祟字占格，部件 −2，`suiCharCount` +1
- [ ] **A3** 农书已收录的组合：**不调用** `F1.Lookup`（用 mock 计数验证为 0 次）
- [ ] **A4** 前 3 步拒绝（locked / occupied / not_enough_parts）**不消耗任何资源**（部件数、铜钱、祟气均不变）
- [ ] **A5** 失败组合不写入农书（`IsLearned` 返回 false）
- [ ] **A6** 铜钱 < 3 且无 `炎` 时，兜底生效：下一次成功合字额外清除 1 个祟字，且不扣铜钱
- [ ] **A7** 存档往返：祟字按田格位置正确恢复；加载后 `suiCharCount` 与场上一致
- [ ] **A8** 同一 tick 内「合字成功」与「祟夜摧毁该田」按固定顺序结算，结果可复现（跑 100 次结果一致）

**跨系统一致性**

- [ ] **A9** `Lookup` 调用参数为 `glyphId` 而非字符（与 F1 A18 的整数键要求一致）
- [ ] **A10** 每次失败都触发 C6 的 `suiCharCount` 变更事件，C6 数值变化符合其公式
- [ ] **A11** 每次成功都触发 C4 的 `Apply`，且 C3 内部**没有任何效果实现代码**（静态检查：C3 文件不出现产出/战意计算）

**体验指标**

- [ ] **A12** 失败惩罚可承受性：单次失败后手牌中仍存在 ≥ 1 个可立即成字的组合（**与 C2 联合测试**，此项无法由 C3 单独验收）
- [ ] **A13** 连续 3 次失败后场上仍有 ≥ 1 个可用字格（否则惩罚过重，需调清除成本）
