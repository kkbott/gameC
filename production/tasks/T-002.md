## 目标

回答一个问题：**Godot 4.7.2（.NET）下，中文字体的动态字形生成与竖排到底能不能用？**

产出一个**书面结论**（可用 / 不可用 / 有替代方案），并留下可复现的验证场景。这个结论会决定 P2 / P3 / P4 三个系统怎么做——所以**先出结论，再谈好不好看**。

> 这条对应 `docs/engine-reference/godot/VERSION.md` 未验证清单第 1 项。Godot 4.7.2 超出多数模型训练数据，**不许凭记忆断言**，必须在本机实测。

## 范围

- [ ] 在 `Client/` 里以 Godot `FontFile` 导入字体，验证动态字形生成；渲染全部 50 字（16 / 32 / 120 px）
- [ ] 记录：图集页数、显存占用、最小字号清晰度、缺字 / 糊边
- [ ] 最小竖排可行性验证：垂直排 5 个字，记录标点位置与行距；明确 Godot 4.7.2 的原生支持程度
- [ ] 尝试**备选路线**：预生成子集图集 / 自定义逐字绘制（二选一，按实测结果）
- [ ] 把结论写进 `docs/tech-validation.md`（新建），含截图路径
- [ ] 截图保存到 `docs/screenshots/font-validation/`

## 不做什么（必填）

- ❌ 不做墨晕 / 飞白 shader（那是 P5）
- ❌ 不做完整竖排排版组件（只验"竖着排能不能排"，不要求标点规则完美）
- ❌ 不改 `design/gdd/` 下任何规则
- ❌ 不改 `Client/Data/*.json`（字表已定稿）
- ❌ 不做 UI 布局、不做 HUD
- ❌ **不许打包任何系统字体**（苹方、微软雅黑等一律禁止，见 P4 R1）
- ❌ 不引入第三方字体管理插件，除非能证明它不扩大维护面（先试 Godot 内置）

## 步骤建议

1. 从 Adobe / Google Fonts 取 Source Han Serif（OFL），放 `Client/assets/fonts/`，**LICENSE 一并入库**
2. 用 `fonttools` 生成子集（避免整包 20,000 字），保留 `_meta` 里的 50 字 + UI 常用字
3. 在 Godot 里导入为 `FontFile`，开启动态字形；在测试场景中用 `Label` 铺 50 字（16 / 32 / 120 px）
4. 用 Godot 的调试器 / 性能面板记录图集页数与显存（具体观测方式以 4.7 文档与实际 UI 为准；记录命令 / 截图）
5. 竖排：先试 Godot 4.7.2 是否有可用的竖排 / 逐字布局能力；没有就写一个最小逐字排布脚本（只验 5 字，不做标点完美）
6. 如果动态字形不达标：试预生成子集图集或自定义逐字绘制，记录两者代价
7. 截图 → 写 `docs/tech-validation.md` 的 T-002 段

## 执行记录（承接人填）

### 结论

**有条件可用**：Godot 4.7.2 .NET 动态字形正常；TextServer 原生竖排可用（不需自定义逐字排布）；50 字 16/32/120 px 无缺字，单字号图集最多 2 页、总显存 5.75 MiB。

### 数据

| 项 | 实测值 |
| --- | --- |
| 字体 | Noto Serif SC（思源宋体同源 OFL 构建）子集 105,080 B / 191 字 |
| 授权 | SIL OFL 1.1，`Client/assets/fonts/LICENSE.txt` |
| 图集页数 | 16px=1，32px=2，120px=1，64px 竖排=1；单字号最大 2（≤4） |
| 图集显存 | 合计 5.75 MiB（单字号最大 4 MiB @120px） |
| 16px 可读性 | 截图 `font-probe-16px-3x.png`（50 字，人工可读） |
| 120px 清晰度 | 动态按 120px 栅格化，无放大；截图 `font-probe-120px.png` |
| 竖排可行性 | 原生 `TextServer.Orientation.Vertical`；5 字 64px 尺寸 (106,384)，标点自动到右上 |
| 备选路线 | 不需要（原生动态字体 + 原生竖排均可用） |
